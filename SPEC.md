# Buddy

Buddy lets you quit a game on one machine and pick up the same save on another. Once a game is set up, pressing **Play** in Steam should be the only interaction a routine session needs. When two machines have made different progress, the player gets to see where each version came from and choose which one to continue.

## Release scope

The first release targets Windows and Linux, including Steam Deck Game Mode. macOS follows. Ship one native Rust executable per platform. The same executable opens the client GUI, wraps a game, runs the CLI or TUI, and can serve the HTTP API. A headless server starts without initializing a window, GPU, or credential store. Server settings live in TOML. All routine account, game, recipe, and backup management goes through the clients.

An account owns its saves, settings files, devices, leases, and backups. Anyone signed into the same server can reuse a file-selection **recipe** that someone explicitly publishes. Publishing shares rules for *where to look*. It never publishes the matched files, local root bindings, credentials, or play history. Each account can edit its own copy.

V1 syncs saves and optionally selected settings files in both directions. Its graphical conflict resolver works on coherent snapshots. A later release adds per-key merging for selected settings formats. Translation scripts, Windows registry capture, and shared multiplayer save ownership are outside v1.

## From installation to the second machine

1. **Connect a device.** In Buddy, enter the server URL, sign in or redeem an invite, and give the device a recognizable name. Default to the hostname. Show the connection result in the window.
2. **Find a game.** Search across installed Steam libraries, Steam shortcuts, and manually added games. Filter by **My setup**, **Shared recipe available**, or **Needs setup**. On a second device, offer the account's existing setup first. On the first device, offer compatible shared recipes and community path suggestions. Show the source of each suggestion.
3. **Choose files.** Show checkboxes, resolved paths, and a preview of matched files and estimated size. Select known saves by default and let the player opt into settings. Offer **Game folder**, **Proton prefix** when applicable, **Home**, and **Browse anywhere**. A game that has never run can have a valid rule with zero current matches. Platform overrides, custom root names, and retention live under **Advanced**. Exact file and subfolder exclusions within a selected location are a future product feature.
4. **Connect the launcher.** Generate a copyable launch option with the actual quoted path to Buddy. For a normal Steam title it has the shape `"/path/to/buddy" run -- %command%`. Infer the Steam app ID at launch, with an explicit game ID available for ambiguous cases. Show how to preserve the user's existing arguments or wrapper. A non-Steam executable can launch directly from Buddy or a generated shortcut, for example `buddy run --game <id> -- <executable> [args…]`. Remember its working directory and arguments on this device. For a Steam shortcut, generate instructions specific to the launcher and runtime. Ludusavi documents cases where the shortcut target itself must be changed. [Ludusavi launch integration](https://github.com/mtkennerly/ludusavi/blob/master/docs/help/game-launch-wrapping.md)
5. **Press Play.** A routine, fast sync opens no window. After roughly one second of waiting, show the current activity, then byte progress when the total is known. Scanning 40,000 small files can warrant feedback even when zero bytes will cross the network. On Deck, every launch-time choice must work with the controller, with a visible safe default and readable device names.

When the recipe may overlap Steam Cloud, explain the overlap during setup. Recommend a single writer for those files on every device and show how to disable Steam Cloud for that title if the player chooses Buddy. Allow disjoint selections. Valve syncs around game sessions and supports suspend-time updates for participating titles. Buddy cannot order its writes against those updates. [Valve’s Steam Cloud documentation](https://partner.steamgames.com/doc/features/cloud)

## Portable file recipes

A game has a stable Buddy ID. Store aliases such as Steam app ID separately. A custom game gets a UUID the player reuses on the second machine. Two shortcuts with similar titles or executable names are suggestions for a match. The player confirms the association.

Each selected file or tree has a stable **slot ID**, a kind (save or settings), and one or more runtime-specific locations. Snapshot paths are relative to the slot. A single-file slot can even have different physical filenames on each platform. For example, this illustrative recipe makes all three locations correspond to the same logical `worlds` tree.

| Runtime | Root | Relative directory for slot `worlds` |
| --- | --- | --- |
| Windows native | Windows Documents | `Example Game/Worlds` |
| Windows game under Proton | Windows Documents inside the game prefix | `Example Game/Worlds` |
| Linux native | XDG data home | `example-game/worlds` |

Built-in roots cover home, install directory, Steam user data for the selected account, Windows known folders, XDG paths, and the game's Proton prefix. Enumerate every registered Steam library, including removable drives and Deck microSD cards. An offline library must not hide the other libraries or imply that its saves were deleted. Resolve the app manifest against its owning library and the selected Steam account. Prefer explicit launch context for a relocated prefix, then look for `steamapps/compatdata/<appid>/pfx` in the game's library. Resolve known-folder redirection, including a Proton Documents link, as a visible local binding. A missing prefix on first launch is a setup state. If a remote save already exists, initialize or bind the prefix and restore it before gameplay. [steamlocate](https://docs.rs/steamlocate/latest/steamlocate/struct.SteamDir.html) · [Valve’s Proton FAQ](https://github.com/ValveSoftware/Proton/wiki/Proton-FAQ) · [Proton’s launch implementation](https://github.com/ValveSoftware/Proton/blob/proton_11.0/proton)

For a non-Steam Minecraft instance, the player might pick an external drive's instance folder and select `saves/My World` under it. Buddy creates a named root such as `instance`. The next device asks once for its own instance folder. The same flow handles a file picked anywhere outside a built-in root. The server only needs the root name and relative selection.

Use the Ludusavi manifest for Steam identifiers, file candidates, save/config tags, and OS/store conditions. Cache a known revision and refresh conditionally. Put discovery behind an adapter and evaluate the existing Rust scanner first. Its maintainers describe the library API as unstable. Import reviewed suggestions into Buddy's recipe format. A manifest refresh must never silently expand an approved selection. Show any registry-only entry as unsupported. [Manifest format and updates](https://github.com/mtkennerly/ludusavi-manifest) · [Ludusavi Rust API](https://docs.rs/ludusavi/latest/ludusavi/)

**Manifest licensing.** Ludusavi explicitly invites compatible implementations and publishes its schema repository under MIT. Include its copyright and permission notice when distributing copied schema or code. The generated catalog also incorporates PCGamingWiki data and Steam metadata. PCGamingWiki publishes its content under CC BY-NC-SA unless otherwise indicated. Individual factual paths and a compiled dataset can have different protection. For Buddy, retain the source and revision on imported recipes, including when sharing them. Clarify dataset redistribution and any commercial use with the upstream rights holders before bundling a catalog or running a catalog mirror. Independently authored recipes work with the same importer. The launch probe uses local Steam metadata only. [Manifest provenance](https://github.com/mtkennerly/ludusavi-manifest) · [Manifest repository license](https://github.com/mtkennerly/ludusavi-manifest/blob/master/LICENSE) · [PCGamingWiki copyrights](https://www.pcgamingwiki.com/wiki/PCGamingWiki:Copyrights) · [U.S. Copyright Office on databases](https://www.copyright.gov/register/tx-databases.html)

The client previews and approves the expanded paths on each device. For recipe edits, use revision checks and show additions, removals, and changed bindings before activation. Cache the approved revision and queue offline edits against their original revision. Concurrent recipe edits get a field-level comparison. Removing a rule stops managing the files and leaves existing local data in place. An unbound or excluded slot carries forward in remote snapshots. Platform-specific or incompatible file formats get separate slots until compatibility is explicitly established.

Treat the selected directory as a filesystem boundary. Validate relative components and perform operations relative to an opened root. Detect overlapping rules, escaping links or reparse points, case or Unicode collisions, and names the target filesystem cannot represent. Stop and show the paths involved before applying anything. Manage regular files and directories. Preserve unrelated files even inside a game folder. A missing drive, denied read, failed scan, or ambiguous Steam account cannot authorize a deletion. [cap-std directory APIs](https://docs.rs/cap-std/latest/cap_std/fs/struct.Dir.html)

## Session protocol

The server keeps one current snapshot pointer, called the **head**, and one lease generation per account and game. Devices retain the last synchronized manifest and its revision, called the **base**. Content comparisons use logical paths and hashes. The server's clock determines lease validity. Session and file timestamps are for display.

1. Take a local lock for the account and game, including offline sessions. Check for an unfinished restore, pending snapshots, or a game process still using the selected paths. Overlapping managed paths on the same OS account also need a local lock across games and Buddy accounts.
2. Acquire the server lease and read the head and recipe revision in one transaction. Start heartbeats immediately and keep them running through scans, dialogs, gameplay, and upload. For initial testing, renew every 30 seconds with a two-minute expiry. Each new grant increments a durable generation. Every head update and release must match the current holder, session, and generation. Updates also compare the expected head and active recipe revision. A delayed request from yesterday cannot overwrite today's world. [Fencing tokens and paused clients](https://martin.kleppmann.com/2016/02/08/how-to-do-distributed-locking.html)
3. If another session owns the lease, show the device, when play started, and its last contact. **Wait** and **Cancel** are available. **Take over…** opens a second dialog naming the displaced device and explaining that it may still be playing. Only **Confirm takeover** sends the request, bound to the observed holder and generation. A change of holder invalidates that confirmation. Preserve an unclosed-session marker after heartbeats expire, including across server restarts. Another device gets the same two-step warning for a suspended or interrupted session. The former device can still preserve its own branch.
4. Reconcile, apply any restore, then record the exact base and session ID durably **before** starting the game. Pass the launcher's executable, arguments, working directory, and environment through without shell reconstruction. Keep credentials out of the child's environment. Forward normal termination requests and preserve the game's exit status. A failed spawn closes the unused session.
5. At verified game exit, scan a stable file set and freeze an immutable local snapshot of changes. Upload missing content and atomically publish the new head **and release the lease**. A no-change exit simply closes the session without rotating history. Retrying after a lost acknowledgment returns the original result. Failed uploads stay visibly pending and survive restarts.

**Offline play.** On an unreachable server, show **Retry**, **Play offline**, and **Cancel**. Play offline uses the cached approved recipe, available local save, and recorded base. Show the device's last successful sync. An empty device expecting an existing remote save needs a restore or a separate, explicit new-game decision. Authentication rejection, certificate errors, corrupt data, and half-applied restores each get a specific error. A mid-game disconnect never kills the game. A device that discovers a takeover before spawning the game returns to the lease dialog. A device that discovers it during gameplay leaves the live files alone. On exit, keep the branch, its base, and its required bytes in a durable local queue until server acknowledgment. On reconnect, submit branches in session order and reacquire before publishing. A stale holder can upload a private candidate without disturbing the current player. Show progress as pending on this device until the server has it.

**Steam Deck and detached launchers.** Quitting via the Deck overlay can kill a wrapper before its exit hook. Suspend can leave a game open for days. Some launchers hand off to an already-running process. Prototype a user-session worker started outside Steam's process scope on Deck, using the same executable and local user-only IPC. Leave the actual game in Steam's launching context for input, overlay, and Proton. Track the session's real process lifetime, including process identity across PID reuse. Windows Job Objects are a candidate where the launcher permits them. For an unobservable handoff, offer **Finish session** after the player closes the game. On power loss or reboot, recover the journal and capture surviving data before the next restore. Recovery can preserve only the bytes the game actually wrote. [Ludusavi’s Game Mode observation](https://github.com/mtkennerly/ludusavi/blob/master/docs/help/game-launch-wrapping.md) · [Windows Job Objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects) · [systemd service lifecycle](https://www.freedesktop.org/software/systemd/man/latest/systemd.service.html)

## Reconciliation and the graphical resolver

Compare the device's observed tree and the current head over the same mapped, approved scope. First verify that the selected roots were scanned successfully. A fresh device with no initialized save differs from an established device that deliberately deleted its last save.

| Observation | Action before play |
| --- | --- |
| First sync, one populated side | Seed from that side. If both are empty, record an empty base. |
| Local and remote contents agree | Record the common state and launch. |
| Local equals base, remote changed | Stage and verify the remote revision, then apply it locally. |
| Remote equals base, local changed | Publish the local revision under the lease. |
| Both changed differently, or both are populated with different data and no known base | Persist both complete candidates on the server as non-expiring backups, then open the resolver. |

Apply this table only to comparable recipe revisions. Preserve the old scope and its captured bytes across a rule change. Present newly added or remapped slots through the first-sync flow. A verified removal of a previously tracked file is an ordinary local change, including when the intended result is an empty tree. A slot this device cannot observe must be inherited from the server when publishing. Show exactly which slots a conflict candidate covers.

A Minecraft world is the unit the player recognizes. Combining one machine's player inventory with another machine's world regions can produce a save neither machine ever played. Default to a whole-save choice even when the divergent edits touched different filenames. Syncthing's per-file conflict copies and block reuse are instructive here. Buddy keeps the conflict copies outside the live game directory. SteamExternalGameSync already demonstrates a controller-driven choice after backing up both sides. [Syncthing’s sync and conflict model](https://docs.syncthing.net/users/syncing.html) · [SteamExternalGameSync](https://github.com/PMahern/SteamExternalGameSync)

The resolver shows two cards with hostname/device label, runtime, session start/end when known, server receipt time, total size, and files added, changed, or deleted since the base. “Last played” is unknown for imported saves. Label times accordingly. Offer **Continue with Desktop**, **Continue with Deck**, and **Decide later**. Both backups survive every choice. Record the chosen result as a new revision with both inputs identified. Recheck the lease and expected head when the choice is submitted. If a third session advanced the head, preserve the old pair and compare with the new head. If the user cancels or the server lacks space for both pins, preserve the local candidate and leave the choice pending.

**Settings files.** V1 offers whole-file settings sync as an opt-in, with runtime-specific slots for machine-specific graphics or device settings. For a later graphical merge, retain the common base's bytes and show base/local/remote values by key. For a declared JSON object, carry over one-sided key edits, coalesce equal edits, and ask about competing changes, including delete/edit. Treat arrays as whole values until the recipe supplies stable element identities. Merge only validated, opt-in formats. Preserve unknown fields and formatting where supported, validate the result, and keep both originals. Reserve a versioned format identifier per slot with an identity (raw bytes) default. This gives future translators a place between local bytes and canonical content without executing server-supplied code in v1. [serde_json](https://docs.rs/serde_json/latest/serde_json/) · [toml_edit](https://docs.rs/toml_edit/latest/toml_edit/) · [diffy three-way text merge](https://docs.rs/diffy/latest/diffy/)

## Incremental storage and safe restore

Use SQLite for server metadata and a directory of immutable content-addressed chunks on local durable storage. Keep a separate SQLite database and chunk cache on each client. A snapshot manifest identifies the recipe revision, format version, slot-relative entries, file sizes, file hashes, and ordered chunk hashes and lengths. A revision records its origin, parent(s), session, and manifest digest. Identical content need only be stored once within an account. Authorize chunk existence checks, reads, writes, and references within the account. [restic repository design](https://github.com/restic/restic/blob/master/doc/design.rst) · [SQLite transaction durability](https://www.sqlite.org/pragma.html#pragma_synchronous)

- **Capture.** Store small files as single chunks. Stream large changed files through FastCDC and hash with BLAKE3. Start benchmarks with 256 KiB minimum, 1 MiB target, and 4 MiB maximum. Version these parameters. Keep memory bounded by chunk size and concurrency. Check the file and directory inventory before and after capture and retry unstable reads. Never publish an incomplete scan as a complete world. [FastCDC streaming implementation](https://docs.rs/fastcdc/latest/fastcdc/v2020/struct.StreamCDC.html) · [BLAKE3](https://docs.rs/blake3/latest/blake3/)
- **Transfer.** Negotiate missing hashes in batches. Upload or download only missing chunks, with bounded concurrency and batched small objects. Persist transfer progress and retry individual chunks. Verify length and digest before admitting bytes to the store. Resume by checking which chunks are already durable. A fully recompressed save can change every chunk, so the full-transfer path must work too.
- **Commit.** Stage immutable objects, flush and publish them durably, then validate manifest completeness and update metadata in a short database transaction. Pins for the two sides of a conflict become visible together. Readers see a complete old or new head. Deduplicate retried requests by operation ID, including a retry after the lease has been released. Enforce quota before commit and preserve the local queue when it fails.
- **Restore.** Preflight free space on each destination volume for changed files and rollback copies. Reconstruct into same-volume staging, reusing verified local chunks, and verify whole-file digests before replacement. Journal the plan, original file identities, replacements, and managed deletions. Recheck for intervening local edits, move originals aside, replace files, and durably finish the group before launch. Keep a recovery path to roll forward or roll back after a crash. A set of renames across several directories or drives has no single atomic switch. Buddy prevents a wrapped launch from seeing a partial restore.
- **Scan cost.** Cache manifests and chunk maps. Where trustworthy filesystem change tracking can prove files unchanged, reuse those entries. After a watcher gap, ambiguous timestamp, disconnected volume, or unclean shutdown, revalidate the affected scope by hashing. Matching size and mtime alone cannot establish content equality. Track bytes read from disk separately from bytes transferred. The former can dominate a warm launch.
- **History.** Keep the head plus the last **three previous distinct committed snapshots** by default. Make the count configurable per game. Offer **Back up now** for current closed-game files, **Keep indefinitely** on an existing revision, **Restore**, and **Delete backup** in the clients. Manual and conflict pins sit outside the rolling count and remain until explicit removal. Restore publishes a new revision through the normal lease flow. Deleting a backup removes its history reference. A head, another pin, active transfer, or pending conflict can still retain the same chunks. Serialize garbage collection against publication and protect in-flight objects. Keep base manifests on devices and bytes needed for outstanding candidates even if rolling server history has expired.

Evaluate `rustic_core` during the storage prototype. It already implements deduplicated restic backups. The deciding test is whether its repository operations fit Buddy's authorization and chunk negotiation while allowing one transactional decision for the fenced head, both conflict pins, and retention. Start with FastCDC and BLAKE3 if integrating the full repository requires a second independently writable source of truth. [rustic_core](https://docs.rs/rustic_core/latest/rustic_core/)

## Rust boundaries and HTTP contract

| Component | Owns | Starting libraries |
| --- | --- | --- |
| Core | Recipe schema, logical paths, three-way comparison, session decisions, manifests, typed commands/events | Serde, FastCDC, BLAKE3 |
| Client runtime | Discovery, device bindings, local database, filesystem transactions, launcher/process adapters, API calls | steamlocate, cap-std, rusqlite, Tokio, reqwest |
| Client interfaces | Render the same pending decisions and progress, return typed choices | iced for windows, rfd for desktop file picking, clap for CLI, Ratatui for TUI |
| Server | Account isolation, catalog, leases, immutable objects, retention and garbage collection | axum, Tokio, rusqlite, Serde/TOML |

Use explicit `buddy gui`, `buddy tui`, and `buddy run` entry points, with the GUI as the default. Steam launches always use graphical decisions. CLI/TUI cover sign-in, discovery, recipe editing, launch/sync, conflict choices, and backup operations. An unattended command returns a decision-required result with a stable ID. It never guesses a winner or silently takes over. Delay UI initialization until something needs displaying. Validate graphical startup on Windows without a console flash and CLI operation with proper console output. [iced](https://github.com/iced-rs/iced) · [rfd platform backends](https://github.com/PolyMeilex/rfd) · [clap](https://docs.rs/clap/latest/clap/) · [Ratatui](https://docs.rs/ratatui/latest/ratatui/)

Use versioned JSON control messages under `/v1` and streamed binary chunk bodies. These are the proposed API groups. [axum](https://docs.rs/axum/latest/axum/) · [reqwest streaming bodies](https://docs.rs/reqwest/latest/reqwest/struct.Body.html)

| Resource or operation | Contract |
| --- | --- |
| Accounts, invites, sessions, devices | Redeem invite, sign in, list/revoke own devices. Client-supplied owner IDs never grant access. |
| Catalog and recipes | Search by alias/title in bulk, fetch or publish an explicit shared revision, fork, and conditionally update private recipes. |
| Game lease | Acquire with head, renew, request/confirm conditional takeover, close or abandon. A busy response includes holder metadata and a challenge bound to the current generation. |
| Uploads, chunks, manifests | Begin an account-scoped upload, batch missing hashes, idempotently PUT verified chunks, fetch authorized chunks, seal a manifest. Uploading alone never moves the head. |
| Head and conflicts | Commit against expected head, recipe and lease. Preserve a fenced-out candidate independently. Pin both candidates and resolve a specific pair against the current head. |
| Backups | List rolling and pinned snapshots, create a pin, restore through a new commit, remove a backup reference. Show whether local work still awaits upload. |

Use `409` for a busy lease or unresolved conflict, `412` for stale revision preconditions, and machine-readable reason codes so interfaces know what to present. Bind idempotency keys to account, operation and payload. Keep protocol and snapshot-format versions explicit so an older client can decline an unsupported restore. [HTTP conditional requests](https://www.rfc-editor.org/rfc/rfc9110.html#name-if-match)

**Authentication.** For a small self-hosted server, start with invite-only accounts and username/password sign-in. A local `buddy admin` command bootstraps the first invite and supports account recovery. Admins can issue subsequent short-lived, single-use invites through the client. Hash passwords with Argon2id, rate-limit sign-in, and issue high-entropy, independently revocable opaque device tokens. Store only token digests on the server and use the OS credential store on the client. If the Deck session lacks an available credential store, offer an explicit owner-readable local credential file or session-only sign-in. The server can serve HTTPS directly, run behind a TLS reverse proxy, or bind HTTP to the configured interface. Plain HTTP beyond loopback prints a startup warning. This assumes a trusted server operator who can read saves. End-to-end encryption can be a separate product decision. [RustCrypto Argon2](https://docs.rs/argon2/latest/argon2/) · [keyring](https://docs.rs/keyring/latest/keyring/) · [Bearer-token transport](https://www.rfc-editor.org/rfc/rfc6750)

## Implementation order and release checks

The Deck hardware trial gates the Game Mode lifecycle adapter. Its trace determines where the final capture and upload run after an overlay stop or suspend. The server, storage, recipe management and desktop clients can proceed independently. The current prototype uses SQLite for account-scoped chunks and transactional history, a desktop process tracker, and a local journal for interrupted sessions. [Run the sync prototype](docs/sync.md) · [Run the Deck trial](README.md#buddy-launch-probe)

1. **Prove the launch boundary on real hardware.** Use a fixture that writes a known save and a launcher that spawns a child and exits. Exercise Windows Steam, native Linux Steam, Proton on a second library, and Deck Game Mode with normal quit, overlay stop, and suspend/resume. Include one real Steam title and a manually bound non-Steam instance. Check controller focus, existing launch options, paths with spaces, and desktop vs sandboxed Steam. Record which integrations can identify exit and finish upload while the player moves to another machine.
2. **Build one complete two-device session.** Account sign-in, one manually bound slot, acquire, pull, launch, exit, incremental push, release, then restore on device two. Route the same conflict decision through GUI, CLI and TUI. Simultaneously start both clients, force a takeover, delay the old client's commit, and verify that its data can be pinned while only the new holder can publish.
3. **Prove recovery and retention.** Cut the connection during upload and after commit acknowledgment is lost. Kill the process during each restore phase, fill a destination disk, sleep through a lease expiry, and keep a device offline past the retention window. Verify byte-for-byte recovery of both conflict versions, idempotent retries, correct head plus three backups, explicit pin deletion, and isolation between two accounts.
4. **Finish discovery and setup.** Add manifest suggestions, custom roots, account-private and explicitly shared recipe revisions, runtime mappings, offline recipe reconciliation, and the searchable game UI. Test a new empty install against a populated server, a missing Proton prefix, an unplugged drive, and two OS users sharing a machine.
5. **Measure before promising launch latency.** Benchmark a 10 GiB world with thousands of files, a sparse edit to one large file, many tiny writes, and a wholly rewritten archive on a PC and a Deck. Record cold/warm scan time, p95 pre-launch delay, network bytes, peak memory, scratch disk, and interrupted-transfer recovery. Target zero payload bytes on an unchanged sync, bounded memory as total size grows, and transfer proportional to changed chunks for the sparse edit. Set a launch-time target from hardware results and keep the progress window responsive throughout.

The first playable milestone is a round trip on two real devices. The v1 release gate is the harder round trip where one device went offline, the player made progress on both machines, and either complete save can still be restored after the player chooses.
